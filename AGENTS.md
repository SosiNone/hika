# AGENTS.md

This file provides guidance to coding agents (Claude Code and others) working in this repository.

## What this is

HIKA: a sci-fi HUD for exploring Swiss hiking routes, built only on swisstopo / geo.admin.ch open data. The product is about **exploring hiking routes**. Do not add race features (race times, leaderboards, cutoffs); the owner explicitly rejected them. The look is inspired by beastydesign.github.io/scifi, which is "all rights reserved": copy no code or assets from it.

## Work

- Bump the version to your own judgement.
- Follow open source best practices and maintain professional grade software.
- Use [tasks](https://taskfile.dev/) to abstract out common commands for the end user. `Taskfile.yml` wraps the npm scripts in `package.json`; when adding a script, add a matching task with a `desc`.

## Architecture

There are three parts, joined by a static data store, the **atlas**:

- **`scripts/`: the build-time pipeline (Node, run with tsx).** `build-atlas.ts` orchestrates `scripts/lib/*` and writes the atlas from swisstopo / geo.admin.ch open data. It writes to `.atlas/v4/` (gitignored), or to a checkout of the data repo (`task atlas ATLAS=../hika-data/v4`). `check-atlas.ts` validates it.
- **The data repo, [SosiNone/hika-data](https://github.com/SosiNone/hika-data).** It holds the built atlas and nothing else, and GitHub Pages serves it at `https://sosinone.github.io/hika-data/v4/`, the same origin as the app. Data refreshes and changed areas ship from there, without an app release.
- **`src/`: the browser app.** It only reads the atlas and never calls geo.admin.ch at runtime. Builds read the published atlas. `task dev` serves `.atlas/v4/` under `/data/v4/` when one is built, else it also reads the published atlas. `DATA_URL` overrides both (`vite.config.ts`).

`src/data/types.ts` (`AtlasManifest`, `Route`, `CatalogueEntry`, `RangeSummary`, `RegionSummary`, `RegionConfig`) is the contract between them, with `src/data/codec.ts` (byte layouts), `src/data/tiles.ts` (the tile grid, windows, stitching) and `src/data/shapes.ts` (the outlines of ranges and areas). The pipeline imports from `src/geo/*` and `src/data/*` except `load.ts`; keep those modules free of DOM code.

`docs/data-coverage.md` tracks which data is in the atlas, which of it the app shows, and what the sources offer beyond that. Update it when you add a source, an atlas field or a panel.

### Atlas format (`v4/`)
- Everything is in absolute LV95 (EPSG:2056) metres. `manifest.json` `format` is the atlas format (`ATLAS_FORMAT` in `src/data/types.ts`, now 4: format 3 had rectangular regions). The app refuses any other format. A new format goes in a new `v5/` next to `v4/` in hika-data, until the app release that reads it is live.
- **Tiles** (`src/data/tiles.ts`) are 5 km squares keyed by their south-west corner in km (`2735_1225`). `manifest.json` lists the tiles that exist (tiles with no data at all, abroad, are left out), and each has three files:
  - `terrain/<key>.bin`: 250 × 250 cells of 20 m, Uint16 **decimetres**, row-major, row 0 = **north** edge, values at cell centres, `0` = no data. swissALTI3D ends at the national border (and leaves out Lake Constance), so windows that reach abroad have `0` cells there. They are skipped, never drawn as 0 m: the point shader and the contour worker drop any cell with a `0` corner, and `TerrainView.heightAt` interpolates over the corners that have data.
  - `trails/<key>.bin`: each swissTLM3D line stored whole, unclipped, in the tile that holds the centre of its extent, so no line is cut at a tile edge. Vertices are whole metres from the tile's SW corner plus `TRAIL_BIAS`.
  - `places/<key>.json`: the swissNAMES3D places in the tile, one per line.
- `routes/<id>.bin` (`encodeRoute`, magic `HKR3`): one whole route, never clipped, with the places its waypoints name. Route ids are `sm-<SchweizMobil id>` (e.g. `sm-951.00`) or `c-<curated id>`, unique across the atlas (`check:atlas`). The app reads and writes `#route=<id>` in the URL, plus `&reverse=1` when the hike is walked to → from.
- `catalogue.json`: every route's meta, stats, bbox, a 24-point altitude sparkline and the areas that list it, its home area first (see Ranges and areas), one per line. The app loads it at boot, for the area lists and the route search.
- `regions.json` (`RegionIndex` version 4): the ranges, the areas (each with the facts the region browser shows) and the arcs their outlines share, one per line. Every border is stored once, in whole decametres, delta-coded; a ring lists arc references (k forwards, −(k + 1) backwards, `src/data/shapes.ts`). `scripts/lib/regions.ts` writes it from `regions/<id>.json`, the partition, the catalogue and the tiles.
- `locator.json` and `switzerland.u16`, the coarse national relief (raw Uint16 decimetres, 2 km), stored once; and `switzerland-1km.u16` (`locator.detail`), a finer relief the region browser fetches when it opens.
- `src/data/codec.ts` is the one module the pipeline encodes with and the app decodes with:
  - Terrain stores gradient-predictor residuals, trails per-line vertex deltas (`HKT2`), routes per-sample deltas.
  - All store 16-bit values modulo 2^16, with the low-byte plane before the high-byte plane.
  - They are deliberately **not compressed** in the file. Git's zlib and the GitHub Pages gzip roughly halve them, and a small upstream change stays a small change that git can delta.
- Rebuilds are reproducible. `build-atlas` rewrites only files whose bytes changed, removes tile and route files no longer in the atlas, and keeps `generated` when nothing changed, so rebuilding unchanged data leaves the data repo clean. Don't add anything that varies per run (timestamps, random order).

### Windows
- The app shows one **window** of the atlas at a time: `loadWindow` (`src/data/load.ts`) fetches the tiles that cover it, stitches them (`stitchGrid`) and clips the trail lines to it. Decoded tiles are kept for the page, and neighbouring windows share most of theirs.
- `routeWindow` is a route's extent plus 2 km (`WINDOW_MARGIN`), on whole km. When the route is opened from an area, it is joined with the area's extent (`bbox`), as long as that needs no more than `WINDOW_MAX_TILES` (6 × 6); most areas are larger, so only the small ones join. Areas don't sit on the tile grid, so a cap on area would let a 27 × 27 km window take 7 × 7 tiles.
- One window can't hold an area's routes: areas are 17–82 km across, and whole routes reach beyond them. So when the selected route leaves the window (`covers`), `main.ts` loads its window and `TerrainView.load` swaps it in place. A later choice of route overrides a window still loading. Hovering a route, and the finish of one that will move on, prefetch the next window.
- `check:atlas` requires every page to cost under 3 MB gzipped in its heaviest window, including the atlas-wide files and the route files the page loads (a region bundle with its imagery cost 2.3–2.5 MB). For an area that is each of its routes' windows joined with its extent where that fits, plus its routes.

### Pipeline facts that were learned the hard way
- swissALTI3D 2 m COGs (found via STAC) have a single 4 m internal overview. `terrain.ts` reads that overview and box-averages it, so `cell` must be a multiple of 4 that divides 1000.
- Trail class (Wanderweg / Bergwanderweg / Alpinwanderweg) and surface exist only in the swissTLM3D Wanderwege **GeoPackage**. The REST layer only flags Alpinwanderweg. The GeoPackage is read with `node:sqlite` plus the hand-written WKB parser in `gpkg.ts` (no GDAL, no sql.js).
- The geo.admin.ch profile service (`profile.ts`): POST the GeoJSON geometry as the raw body with `sr`/`nb_points` in the query string. It is limited to 5000 points, keeps input vertices and may add extra points, so results are matched back by coordinates.
- SchweizMobil routes come from the Wanderland Schweiz GeoPackage (`loadWanderland`), from the FSDI download service, not from one API request per route.
  - Its `Etappe` rows are the stages, with ids `<NrR>.<NrEtappe>` as the API numbers them (`1.01`, `951.00`).
  - A few stages come twice, as two versions of the whole stage; the first row is kept, as merging them would walk the stage twice.
  - The build logs a stage whose chained length is more than 20 % off SchweizMobil's own (`DistanzE`).
  - It holds 976 routes and stages: national, regional, local, and barrier-free trails (`handicap`, numbered like local routes).
  - The file keeps its name across releases, so it is cached per data date.
- Stage geometries are unordered MultiLineStrings. `chain()` joins them, but walks no step wider than `MAX_GAP` (1 km), whether a gap between parts or one straight segment: some stages cross a lake by boat, drawn as a straight line or left out (ViaGottardo 7.07 is 4 km of walking around a boat trip from Luzern to Altdorf). The longest walked piece is the route. A gap between parts can also be a hole in the data, and then walked trail is lost: 893.00 keeps 6 of SchweizMobil's 10 km, and 638.00, 813.00 and 922.00 lose 1.3–2.9 km. The owner chose that over a straight line drawn across the gap; the build log lists every stage the rule shortens. Then the route is oriented by geocoding its "from" and "to" near the route's own midpoint; where only one end is found, it decides alone. Routes are kept whole.
  - SchweizMobil names ends its own way, so they go through `resolveRouteEnd`: "Lugano (Comano)" is Comano, "Cap. Pairolo" the Capanna Pairolo, "Urner Boden" Urnerboden.
  - Those variants must match a place's whole name: the "Station" of "Glaris (Station)" would otherwise prefix-match any station and turn the route around.
  - The few routes where neither end is found keep their chained direction; the build log lists them. Loops, which start and end at the same place, have none to find.
  - A route can come out backwards silently, which only shows as swapped climb and descent, so check them after changing the orientation.
- Routes with less than half their length in Switzerland (`MIN_SWISS`) are left out, because swissALTI3D has no terrain beyond the border. These are Liechtenstein's own routes and some stages in Italy and France, 26 in all. A route any area excludes (`excludeRoutes`) is left out too.
- Curated hikes in `regions/<id>.json` name their via-points. These resolve through swissNAMES3D (`resolvePlace`, with an optional `kind`) among the places in their area or within 5 km of it, nearest its label point, and are routed with Dijkstra on `TrailGraph`, using Swiss hiking time as the edge weight, over the trails within 5 km of their stops.
- swissNAMES3D has the outlines of its areas (ranges, landscapes, valleys …) only in its **GeoPackage**, from the 2026 release on: the CSV that `loadPlaces` reads has one label point per area. `loadAreaFeatures` (`names.ts`) reads them, and merges the language variants, which are rows with the same uuid and geometry. A bare place name can match a tiny namesake exactly and win over the real one's longer name ("Stoos" is a hamlet; the village is "Stoos SZ"), so check where `task regions:preview` says a place seed lies.
- Every route gets DEP/ARR waypoints: the nearest named place, else a place named after the route's end.
- `finishRoute` (`scripts/lib/route.ts`) samples, heights, classifies and times every route.
- **Fair use.** The geo.admin.ch REST services (api3, and the STAC API on data.geo.admin.ch) allow 40 requests a minute under the FSDI terms, so `fetchCached` (`scripts/lib/http.ts`) spaces requests that miss the cache 1.5 s apart. File downloads (the swissALTI3D COGs, the GeoPackages) are the download service those terms send bulk use to. A first national build therefore takes hours, and later builds hit the cache. Don't remove the pacing.
- **Footprint.** `build-atlas` covers Switzerland: every tile with Swiss ground (`swissGround`, a 500 m grid tested against the border), the window of every route, and its window joined with each area that lists it (where that fits). That is 1,944 tiles (48,600 km², 1,865 of them with data) and 1,016 routes (950 SchweizMobil, 66 curated), 296 MB. A first build takes about 1.5 hours at the fair-use pace; a rebuild from the cache about 10 minutes. `--region <id>` builds only that area and the routes it lists, for trying out a change (the atlas in the output directory then holds just that; the areas are still cut nationally). `--dry-run` only measures the footprint.
- `check:atlas` checks:
  - that tiles decode, and every line and place sits in its tile;
  - coverage: no 1 km block missing well inside the border, and under 1 % empty cells inside Switzerland;
  - every route (`routeProblems`): lengths, altitudes, times, climb drift, waypoints, and terrain under every sample inside Switzerland;
  - that the catalogue matches the route files;
  - `regions.json` against `regions/` and the catalogue: ids and aliases unique, ranges with areas, outlines that decode and tile Switzerland (a 2 km grid, each point in exactly one area and in that area's range), and every route listed in a home area that holds the most of it and in others that hold their `minInside` share;
  - the size of the 1 km relief;
  - the window budget.

### Swiss hiking time (`src/geo/hikingTime.ts`)
`PACE` is a table digitised from the official Schweizer Wanderwege isochrone chart (4.2 km/h on the flat, fastest at about −5 %). It is not a rule of thumb; don't replace it with one. Slope comes from altitudes smoothed over about 60 m, and signpost display rounds to 5 min.

Route `stats` are computed in the pipeline (`finishRoute`). The per-sample cumulative series (`km`, `minutes`, `up`, `down`) are re-derived on load (`deriveRoute` in `src/data/load.ts`). `reverseRoute` builds the to → from view from the same samples and helpers (time = `timeBack`); `main.ts` caches it, so panels can cache on the route object rather than its id. Both sides must use the same helpers (`routeClimb` in `src/geo/track.ts`, `cumulativeMinutes`), so the route list and the preview panels show the same numbers. `check:atlas` fails if the stored climb totals drift from `routeClimb`.

### Rendering (`src/gl/`)
- World space: x = east, y = up, z = **south**, origin at the centre of the window shown. `TerrainView.world(e, n, alt)`, `ground` and `heightAt` take LV95, like every route and place in the app; the window's trails are stored in metres from its corner. Grid cell `i` sits at `(i + 0.5) * cell`. `TerrainView.load(window)` swaps the window in place: it moves the camera with the origin (`OrbitCamera.shift`), so it stays over the same ground, and makes the new window's overview the home (double-click).
- Vertical exaggeration is applied **in the vertex shaders** (`uExag`, `uBase`), so CPU-side geometry (trails, contours, ribbons) stores raw altitudes and never needs rebuilding.
- The point cloud has no vertex buffer and one colour mode: the owner dropped the SWISSIMAGE mode in 0.13, because orthophotos would add about 95 MB to national data for a mode few used. Points come from `gl_VertexID`, which samples an `R16UI` height texture, with jitter, depth-of-field point size and distance fade. Stride 2 applies beyond 16 km camera distance.
- The scene has no depth test: points and contours are additive, network and ribbons are blended over them (hologram look). The one exception is inside a route ribbon, where the depth buffer only decides which of its overlapping segments owns a pixel (see below). Contours are computed in `contours.worker.ts`.
- The trail network is instanced: one screen-space quad per segment, so its width holds at any DPR (`GL_LINES` is always 1 device pixel). Like a printed map, it is drawn twice: first a casing in the background colour that clears the point cloud underneath, then the class colours. The selected route is a screen-space ribbon coloured per segment by trail class (`uByClass`, off-network segments in `gl.hover`) with its own casing, wider than the network, so it reads above it even where it runs on top of a trail of the same class. The owner found an accent outline around it and wider ribbons too heavy. Ribbons are instanced too, but each segment is a capsule (round ends), so segments meet in round joins. They are drawn opaque, and each fragment writes its distance from its segment as depth, so the nearest segment owns every pixel: segments are often shorter than the ribbon is wide, and without that, overlapping antialiased edges would double up. A hovered route is the same, a little thinner. Both ribbons narrow to about half their width as the camera pulls back from 4 to 16 km (`RIBBON_SHRINK`), because full-width ribbons swamp the overview.
- The owner found the full network overwhelming, so by default only the trails branching off the selected route are drawn. `TerrainView.trailMode` is `'auto'`, `'all'` or `'off'`, and is cycled by the TRAILS button in the stage toolbar. In `'auto'` the network fades with walking distance along the trails from the selected route (fully shown within 300 m, gone by 5 km, `NETWORK_REACH`), at any zoom. `TrailNetwork` (src/geo/network.ts) computes that distance per vertex with a multi-source Dijkstra when the route changes; it feeds the per-instance `aNear` attribute. A newly selected route loads its trails: a front runs out along them to 5 km in 1.8 s (`LOAD`), with a short head in the accent that dims with the reach, while the trails of the route before (`aPrev`) fade out over 0.4 s (`UNLOAD`). The fragment shader takes the walking distance from whichever end of a segment is nearer, so the front sweeps along long segments too. Switching TRAILS to AUTO loads them again. None of it moves under `prefers-reduced-motion`.
- `OrbitCamera` (src/gl/camera.ts) slowly circles its target when left alone (`spin`, off under `prefers-reduced-motion`). Any drag, wheel or double-click pauses it until the pointer has been still for `resume` seconds. A `flyTo` without `az` leaves the azimuth free so the orbit keeps turning; one with `az` (reset) pauses it. Once the user pans or zooms (`framed`), the playlist moving on by itself keeps their view; choosing a route (list, map, skip) or double-clicking flies again.
- On touch screens the map takes every gesture (`touch-action: none` on `#terrain`, so the page scrolls around it): one finger orbits, two fingers pinch to zoom and drag to pan, and a double tap resets (caught in `attach`, as not every touch browser sends `dblclick`). A tap selects a route with more slack than a click (10 px of movement, 24 px pick radius), and a gesture that ever had two fingers is never a tap (`RoutePicker`, below). A view narrower than `minAspect` (1.2:1, a phone held upright) widens its vertical field instead of losing the sides, so fly-to framing and the home view need no per-device distances. `test/camera.test.ts` covers the gestures and the field of view.
- `RoutePicker` (src/gl/picker.ts) picks routes on the map with `pickRoute` in `main.ts`, the nearest route sample within the pick radius. A click or tap selects that route. A resting mouse hovers it, the same hover ribbon as the route list, with a pointer cursor, so the map shows what a click would select. Not while a drag orbits or pans: the hover clears once a press moves like a drag (4 px) and comes back on release. The hover is picked in the render loop, on the frame after the mouse moves and every 100 ms while it rests, so it follows the idle orbit, but not during a fly-to, which would flash every route it sweeps past. Hover ribbons are cached per route view (`TerrainView.ribbonOf`). `test/picker.test.ts` covers it.
- A scan line sweeps the terrain between the grid's lowest and highest altitude (`scanAlt` in `render`). The stage's altitude meter (`.alt-meter`, built in `mountStageOverlay`) follows it.
- Labels, the hiker and the crosshair are drawn on a separate 2D canvas (`src/hud/labels.ts`) by projecting with the frame's view-projection matrix. Text, leader lines and markers are drawn without a halo or outline (the owner found outlined marks too heavy); they sit on the background between the sparse points, which is why `test/theme.test.ts` checks label colours against `bg`. Only the hiker callout and the hover readout get a background plate. Route waypoints are kept subtle, like the pins of the hud-console-framework demo: a level ring on the ground around the track (sized by camera distance, so it keeps its screen size but lies flat), a thin leader up to a small hollow circle, and the plain ID and name beside it. They show passed / next / ahead relative to the preview hiker; only the next one takes the accent, and its ring breathes (`nextWaypoint` in `src/data/load.ts`, shared with the waypoints panel). The hiker is a filled arrowhead (`pointer` in `src/hud/pointer.ts`, the same shape the charts use) aimed over ±60 m of track and low-pass filtered in time (`smoothHeading`), with a sonar ping and a telemetry callout; the ping stops under `prefers-reduced-motion`. Hovering the elevation profile puts the same arrowhead, outlined, on the map. Like the ribbons, these markers (hiker, ping, hover arrowhead, waypoint pins and rings) shrink to under half their size as the camera pulls back from 4 to 40 km (`MARKER_SHRINK`, handed to the label layer as `RenderInfo.markers`); text keeps its size.

### Theming (`src/theme/`)
- One visual language, **paperlab** (flat greys ported from LosEcher/hud-console-framework, with a glacier-cyan accent), in two **schemes**: dark (the default, `DEFAULT_DISPLAY`) and light. The owner chose to drop the theme (accent) and style layers and the old teal `phosphor` look. Don't bring back a theme or style picker.
- `tokens.ts` is pure data (`SCHEMES`, `TRAILS`) plus `resolve()`. The saved choice (localStorage) is overridden by `?scheme=`; `?region=` picks the area and the hash belongs to `#route=`.
- `apply.ts` sets the CSS variables and mutates the shared `palette` (re-exported as `COLORS` in `panels/common.ts`). Canvas and WebGL code reads `palette` / `palette.gl` and never hard-codes a colour; inline HTML uses `var(--…)`. The `:root` values in `hud.css` mirror the default display for the first paint.
- The light scheme draws the terrain with premultiplied over-blending (`gl.blend: 'over'`), because additive light washes out on paper.
- Trail-class colours (`TRAILS`) are the official Swiss signpost colours. They are adjusted only for contrast per scheme and never follow the accent. The owner wants the accent to stay clear of them: `test/theme.test.ts` checks contrast for both schemes and requires the accent to keep its distance from every trail colour, also for red-green colour-blind viewers. That rules out reds, oranges, yellows, blues and violets.

### App state and panels
- `Store` (src/state.ts) is a tiny observable. `main.ts` reacts to `routeId` / `hoverRouteId` / `display` changes via `subscribe`.
- The preview position `store.state.minute` is **mutated directly** in the render loop, without notifying, for performance.
- Panel A (Route player) plays the area's routes as a playlist (`Playlist` in `src/playlist.ts`, in the route list's `CATEGORY_ORDER`). `ctx.skip(±1)` changes route; "previous" first rewinds a route that has played for over 2 s. At the finish the loop holds 2.5 s, then repeats the route (`repeat`) or moves on. `shuffle` walks a random queue that starts at the current route. Space and ← / → are handled on `window` unless a control has focus.
- Each `mount*` function in `src/panels/` builds its DOM once and returns an update callback. `main.ts` polls all of them about every 50 ms, and they rebuild static parts only when the route id changes.
- Small screens are handled in `hud.css` alone; `index.html` keeps the desktop column structure:
  - Up to 1100 px the page scrolls: the map first, then the profile and gradient side by side, then the panels two by two.
  - Up to 640 px (phones) `.col` and `.row-bottom` become `display: contents`, so `order` can put the route player straight under the map, then the profile, waypoints and routes, then the other panels.
  - `(pointer: coarse)` enlarges the controls a finger has to hit, and `(hover: none)` swaps the map's mouse hints for touch hints.
  - Hover-only behaviour stays mouse-only (the route list's and the map's hover ribbon check `pointerType`). The elevation profile takes pointer events, so a finger dragged along it scrubs the hiker while vertical swipes still scroll.

### Ranges and areas
- The entry points into the atlas are **areas** (`region` in the URL and the code), grouped into mountain **ranges**. The owner chose this over the 24 × 19 km boxes of format 3, picking areas as valleys and landscapes (borders on ridges) and the range first, then the area, in the browser.
  - The ranges are swisstopo's 10 Grossregionen in swissNAMES3D (`RANGES` in `scripts/lib/areas.ts`, with English titles; `names` holds the official ones), which tile Switzerland.
  - The 54 areas (`regions/<id>.json`) tile Switzerland too, so every route belongs to one. They carry no data of their own, so the same route can be on several areas' lists.
- **How the areas are cut** (`buildPartition` in `scripts/lib/areas.ts`; the work is in `scripts/lib/partition.ts`), on a 200 m raster of Switzerland:
  - An area's `seeds` are swissNAMES3D outlines (`{ name, kind }`: a Landschaftsname, Haupttal, Huegelzug or Massiv; every feature of that name, or the one nearest `near`), discs around places (`{ place, kind }`, through `resolvePlace`) or around points (`{ at }`). Where outlines overlap, the smaller wins.
  - Areas grow from their seeds by Swiss hiking time (`segmentMinutes`, lakes 4 × slower) over a 200 m terrain model (`nationalDem`, box-averaged from the cached 20 m blocks of the same STAC searches as the tiles), a multi-source Dijkstra: every cell goes to the area whose seed is the fewest minutes away. So borders land on ridges, rock walls and lakes, and a valley stays whole.
  - A seed inside another area's seed could never grow, as seeds cost nothing to cross: `paintSeeds` fails the build when an area keeps under half of its seed, or has almost no free ground around it. So a catch-all outline (Rhonetal, Rheintal, Surselva, Sopraceneri) can only seed an area when no other area's seed lies inside it.
  - Pieces under 2 km² go to their neighbour; larger exclaves stay, and the build log and the preview list them.
  - An area belongs to the range holding most of its cells, unless its config sets `range` (`alpes-vaudoises`, `alpstein`, `uri`). Grossregion borders run along valley floors (Goms is 47 % Berner Alpen), so areas are not clipped to their range: a range is the union of its areas, under its official name.
  - Borders are traced along the cell edges, split where three areas meet, simplified to 150 m (`traceArcs`) and stored once, so neighbours share them exactly.
- A route lists in its **home area**, the one holding most of its length (`regions[0]`), and in any other holding at least its `minInside` share and `minInsideKm` (0.3 and 2 km everywhere), so ridge and pass hikes show on both sides. A curated hike's home is the area that defines it.
- `regions.json` carries each area's outline, label point, extent and the facts the browser shows (`classics`, `trailKm`, `hardKm` and `alt`, measured inside the area), and each range's outline, areas and route count.
- The app boots from the atlas (`loadAtlas`): `pickRegion` (src/regions.ts) takes `?region=<id>`, or a former id (`aliases`: the format 3 regions `hasliberg`, `jura`, `schwarzsee` and `simplon`), else `DEFAULT_REGION` (`alpstein`, so links from before regions existed still open the right hike), else the first area. The route comes from `#route=`, else the area's `defaultRoute`; a `#route=` the area doesn't list opens the route's home area. `main.ts` then puts the area's id in `?region=`.
- One area is shown at a time, with all its route files loaded (`loadRoutes`). Switching (`ctx.goToRegion`) is a page load of the `?region=` URL (`regionHref` keeps `?scheme=` and drops the hash), so the back button returns to the previous area. The region button is the brand subtitle in the top bar, "AREA · RANGE" (`mountRegionPicker`).
- The region browser (`src/ui/regionBrowser.ts`) is a native `<dialog>`, opened by the region button, the G key, the expand button on the locator (G), and a range in the locator. It has two levels:
  - The whole country: the map and the list show the ranges. One lights up under the pointer, and a click zooms into it.
  - Zoomed into a range (`SwissMapOptions.focus`, an eased change of view): the list shows its areas, the rest of the country recedes, and the head has a back button. A click opens an area. On touch, a tap on the map first picks the area and a tap on its list entry (or the same area again) opens it. Escape clears the filter, then zooms out, then closes.
  - The filter searches the areas by title, subtitle, official names in any language ("conches" finds Goms), former ids, cantons (code or name) and range (`filterRegions`), listed under their ranges; when they all lie in one range, the map zooms into it. From two characters on it also searches every route in the catalogue (`filterRoutes`: number, name, start and end). Up to 40 routes are listed below the areas, keyed `r:<id>`. The filter is only autofocused on a fine pointer, so a phone keyboard doesn't cover the list. On phones the dialog is full screen.
  - The map and the list share one active entry, and ↑ / ↓ / Enter move over every visible option. An active route lights up its home area and is pinned on the map (`SwissMapOptions.mark`).
  - It is the locator tile (G) grown, so it has the same title ("Switzerland") and the same map at the same angle. It always opens on the whole country and shrinks back from it; opened from a range, it zooms in once open. However it is opened, it grows out of the tile, and every way of closing it (✕, Escape, the backdrop, the current region) shrinks it back via `shut()`. This is a view transition (`morph`): the tile and the dialog take turns holding the view-transition name `region-browser`, so the browser animates one box between them while their pictures cross-fade, and their map canvases hold `region-browser-map`, so the map moves on its own from the tile's body to the browser's map pane (styled in `hud.css`). Only one element may hold a name at a time, or the transition aborts. The browser draws the map at the tile's sway angle, and the tile holds that angle (`Sway.held`) while the browser is open, so the map neither turns while it grows nor when it shrinks back. It doesn't straighten: turning the browser's large relief would redraw it every frame, too slow for the transition at 2× pixel density. With the tile scrolled off screen (phones), the browser zooms in and out on its own, as one picture. Without the View Transitions API, or under `prefers-reduced-motion`, it opens and closes at once.
- The locator (G) and the browser draw the same map, `SwissMap` (`src/hud/switzerland.ts`), with one projection (`TILT`) and one `Sway` (created in `main.ts`):
  - The national relief is a point cloud. Lakes are solid patches, found by `lakeCells` (`src/geo/relief.ts`) from the flat cells of `switzerland.u16`.
  - The browser fetches a 1 km relief (`locator.detail`, `loadDetailRelief`) when it opens and draws on it once loaded, so a range zoomed into keeps its valleys. While the view zooms, the last relief image is scaled; it is drawn again once the view settles.
  - The border, the canton borders and the arcs are draped on the relief (`reliefAt`, altitudes smoothed along the line; an arc keeps its ends at the raw relief, so the arcs meeting there still meet), and the areas and ranges are assembled from the draped arcs, so an area lies on the mountains it covers.
  - Range borders have a background casing, like the trail network; the borders between the areas of a range are hairlines.
  - A range or area under the pointer glows: its relief is drawn again, brighter (`lighter`; `multiply` on the light scheme), under a faint accent fill and an accent outline. The current area is lit the same way and pulses at its label point; its range is outlined in the accent.
  - Hit tests take the outline as drawn that holds the point (`hitTarget`), an area before a range, and allow a finger some slack. Labels are centred on each shape's label point (`placeAt`).
  - The current area has a wedge showing the 3D camera's footprint (`cameraCone`, using `OrbitCamera.hfov`).
  - The locator's targets are the ranges: one lights up under the pointer, and a click opens the browser zoomed into it. It sways, but not under the pointer, while a range is picked, or under `prefers-reduced-motion`. On touch its first tap names a range and shows an EXPLORE button.
- Lingering on an area (200 ms) in the browser's map or list calls `prefetchRegion`. It adds `<link rel="prefetch">` for the tiles of the window the area opens with and for its route files, skipped under Save-Data.
- To change or add an area:
  1. Edit or write `regions/<id>.json`: title, subtitle, cantons, `seeds`, curated hikes, and where needed `range`, `defaultRoute` and `aliases`.
  2. Run `task regions:preview`. It cuts Switzerland from the download cache in about 15 s, prints each area's route count (aim for 12–45; Valposchiavo, a valley of its own, has 9), the exclaves and the curated stops that lie in another area, and draws `.cache/regions/preview.svg` (`-- --routes` adds the routes, `-- --range <id>` zooms in, `-- --places <id>` lists an area's places for writing curated hikes).
  3. Run `task atlas ATLAS=../hika-data/v4` in a checkout next to hika-data, and commit the changed atlas there. Its Pages deploy publishes it; the app needs no release.

  Areas share the ground, so a change moves the borders of its neighbours: check the whole range in the preview. Curated hikes should add something SchweizMobil doesn't already have, so check the build log's route list first.

## Deploy

`.github/workflows/pages.yml` deploys on release tags (`v*`, plus manual `workflow_dispatch`), not on pushes to `main`. It fails unless the tag equals `v` + the `package.json` version, runs the same checks as CI, builds with `BASE=/<repo>/` and publishes `dist/` to GitHub Pages. Release from `main` with `task release BUMP=<patch|minor|major>` (`npm version` + `git push --follow-tags`); the `create-release` skill in `.claude/skills/` walks through the whole flow. `.github/workflows/ci.yml` runs `typecheck`, `test` and `build` on pull requests and on every branch push (tags don't trigger it).

The atlas deploys separately from hika-data: a push to its `main` publishes it with its own Pages workflow, after `check:atlas` (run from a checkout of this repo). An app release that reads a new atlas format must wait until that format is published.
